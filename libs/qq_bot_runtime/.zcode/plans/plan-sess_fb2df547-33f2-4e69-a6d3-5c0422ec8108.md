# 跨平台人物记忆打通(QQ ↔ MC)实现方案

## 目标
建立「身份绑定层」:QQ 号与 MC 游戏名(未来可扩展 console/B站等平台)经双向确认绑定为「同一个人」后,bot 在任意一侧都按同一个人的键读写**人物档案(user_profiles)、重要笔记(important_notes)、全文历史(chat_history jsonl)**,并在对话中注入另一侧的称呼/身份提示。未绑定的人与现在完全一致;主人(2190720017↔insomnic)由预置 seed 直接激活,替代 mc_bot_brain.py:36-37 的硬编码。

## 一、新增 identity.py(身份注册表,核心)
- 数据文件 `identity_bindings.json`(项目根,与 user_profiles.json 同约定)。结构:人员列表,每条含 aliases[{platform,id}](qq 号 / mc 游戏名小写)、state(active / pending_qq / pending_mc)、canonical(记忆合并键:含 QQ 则=该 QQ 号,否则=最早 mc 名,保证旧数据零迁移)、时间戳。
- API:
  - `canonical_for(platform, raw_id) -> str`:经 active 绑定解析出 canonical 记忆键;无绑定原样返回(行为不变)。
  - `lookup(platform, raw_id)` / `aliases_of(canonical)` / `hints_for(platform, raw_id)`:身份提示与待确认提示文本。
  - 绑定操作:QQ 侧发起 `request_bind_mc(qq, mc名)` → pending_mc;游戏侧声明 `request_bind_qq(mc名, qq号)` → pending_qq;`confirm_mc(mc名)`(游戏侧确认)、`confirm_qq(qq号)`(QQ 侧回复同意)、owner `force_activate`(主人直接批准)、`unbind`、`list_for`。
  - 冲突规则:alias 已被 active 占用则拒绝新绑定;激活时调用 long_term_memory.merge_alias_history(幂等)把该 mc 名的旧历史并入 canonical。
- 并发:identity 文件可被核心进程与 mc 进程双写(低频),load-modify-save 用共享文件锁(msvcrt on Windows + 无锁降级)。
- 预置:文件不存在/为空时,从 config 生成主人绑定(PROACTIVE_PRIVATE_USER_ID ↔ IDENTITY_OWNER_MC_NAMES)为 active 并触发历史合并。
- 开关 `ENABLE_IDENTITY_LINK`:关闭时 canonical_for 原样返回、命令禁用、提示不注入(完全回到现状,但主人硬编码也随之移除——因此默认 True)。

## 二、config.py
- `ENABLE_IDENTITY_LINK = True`
- `IDENTITY_OWNER_MC_NAMES = ["insomnic"]`(替代 mc_bot_brain.py:37 硬编码)

## 三、记忆文件并发安全(两个进程都会写的文件)
- `long_term_memory.py`:新增 `merge_alias_history(alias, canonical)`(幂等:读 alias jsonl → 行改写 user_id=canonical 后追加进 canonical 文件 → alias 文件 rename 为 .merged,全程文件锁);给 update_profile/replace_profile 的 load-modify-save 加文件锁。
- `important_notes.py`:add_note 等 load-modify-save 流程加同一文件锁。

## 四、chat_service.py(QQ/核心进程)
- 新增命令(置于「触发判断」之前的命令区):
  - `/绑定 mc:<游戏名>` — 本人 QQ 发起绑定(转 pending_mc,等游戏侧同名玩家确认);名字已被占用/已绑定会明确提示。
  - `/绑定列表` — 查看自己 QQ 的 active/pending 绑定;主人额外可用 `/绑定总览`。
  - `/绑定批准 mc:<名>`(主人)、`/解除绑定 mc:<名>`(本人或主人)。
  - 文本确认:QQ 有 pending_qq 待确认时,回复「同意绑定/确认绑定/同意/是」→ confirm_qq 激活;回复「不是/拒绝」→ 拒绝。
- `_chat_pipeline` 记忆注入区追加 `identity.hints_for("qq", user_id)`:已绑定 →「此用户在 MC 世界里是 XX,直接当同一个人接话;注意别把 QQ 私密信息说进公开游戏频道」;有待确认绑定 → 小字提示引导(用户已回应后停止)。
- 实时动态注入(约 1035-1041 行)条件由「仅主人」放宽为「主人 或 该 QQ 已 active 绑定 mc 名」,绑定好友在 QQ 上也能看到游戏现场(在线玩家/最近对白)。

## 五、mc_bot_brain.py(游戏进程)
- 删除 MC_OWNER_GAME_NAMES 硬编码与 is_owner_name 的集合判断,改走 identity(主人语义不变:canonical 的 QQ == PROACTIVE_PRIVATE_USER_ID,escort 照常)。
- `_load_memory_digest(game_name, text)` 重写:
  - active 绑定且含 QQ → 组装身份提示 + 该人 QQ 档案/笔记(build_memory_messages)+ QQ 近况(摘要/话题/最近对白)+ 之前的游戏对白(canonical 历史文件)。QQ 近况改为每次 fresh 加载 Memory(30s 缓存),顺带修复长期运行后主人快照陈旧的问题。
  - 无绑定 → 维持今天陌生人逻辑(按原名)。
  - pending_qq → 注入「该玩家声称 QQ 号 xxx,等 QQ 侧同意」。
  - 提示词约束:QQ 私密事实不要在其他玩家面前说(游戏频道公开)。
- `_pull_game_chat` LLM 之前加规则解析(可靠、不烧 token):
  - 文本匹配「绑定QQ <数字>」/「QQ <数字> 是我」→ request_bind_qq,游戏内 say 一句结果。
  - 该 mc 名存在 pending_mc 且(bot 刚问过确认 10 分钟内 或 文本为「确认绑定/同意绑定」)→ confirm_mc 激活 + say;匹配「不是/不是我」→ 拒绝。
  - 文本「记住:xxx」/「记下:xxx」→ 直接 important_notes.add_note(canonical)(游戏侧也能给绑定人记笔记,与 QQ /记住 同源)。
  - 处理结果同时注入会话,保持上下文自然。
- 写回:user 行(mc_bot_brain.py:653)与 assistant 行(约 388)统一用 canonical 键写 chat_history(jsonl append,并发安全);未绑定玩家 canonical=原名 → 行为不变。

## 六、历史合并时机
- 主人 seed 激活(首次运行)→ insomnic.jsonl 并入 2190720017.jsonl(幂等 .merged)。
- 任意新绑定激活(QQ 或游戏侧完成确认)→ 激活方进程执行 merge_alias_history(幂等+锁,两进程同时激活也只合一次)。

## 风险与边界
- 不引入跨进程共写 memory_data.json(短时记忆按渠道保持,融合在档案/笔记/历史层)。
- 群聊/私聊现有语义、未绑定玩家、汇报与监控通道均不受影响。
- 误绑定可随时 /解除绑定;解除后不再融合新数据(历史不拆分)。
- 待确认绑定只影响该 QQ 本人会话,不泄露给第三方。
