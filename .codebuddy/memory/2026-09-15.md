## 追加：修复流式回复被截断/展示不完整
用户反馈"智能体发消息时有时会被截断消息展示不完整"。定位出 3 个真实缺陷并全部修复：

1. **【主因】callbackFlow 缓冲溢出丢字**：`streamChatFlow` 用 callbackFlow（默认缓冲仅 64），
   而回调运行在 OkHttp 网络线程（非挂起），模型吐字快而 UI 消费稍慢时 `trySend` **静默失败** → 中间文字被丢。
   **修复**：流末尾加 `.buffer(Channel.UNLIMITED)`。
   （注意：`send()` 是挂起函数不能在 OkHttp 回调里用，`trySend` + UNLIMITED 才是正解；
   别试图手写 callbackFlowWithUnlimitedBuffer 包装，直接用官方 `.buffer()` 即可。）
2. **异常时已收内容被整体覆盖**：原来 catch 里直接 `updateAssistant(...,"（出错了：xxx）")` 把半截回复全丢了。
   **修复**：catch 内保留 `sb.toString()`，只在末尾追加「（回复中断了：xxx）」；且中断内容**不写入历史与向量记忆**
   （避免把错误提示污染成长期记忆）。
3. **finally 用当前 state 回写文本**，并发下可能把已渲染内容回退成早期版本。
   **修复**：finally 只置 `isSending=false`，正常结束才在 try 体外统一更新为完整文本。

## 【关键修复】截断问题真凶（2026-09-17）
用户反馈"输出还是会被截断"——即 v1.0.1 的修复**不彻底**。深挖后找到真正的根因（此前误判）：

### 真凶 1（主因）：`while (!source.exhausted())` 用法错误
`exhausted()` 是**非阻塞探测**：语义为"当前无缓冲数据且源已到末尾才返回 true"。
网络流中 socket 缓冲**暂时为空**但连接仍存活时，它也可能返回 true → **循环提前退出，后续内容全丢**。
→ 正解：`while (true) { val line = source.readUtf8Line() ?: break }`（null 才是真 EOF）。
**这是上次 `.buffer(UNLIMITED)` 没解决问题的原因**——丢字发生在更前面的读取环节。

### 真凶 2：OkHttp 默认 readTimeout 仅 10 秒
流式响应中模型"思考"停顿超 10 秒（排队/推理型模型/长回复间隙）会被静默掐断。
→ 正解：`connectTimeout 30s / readTimeout 5min / writeTimeout 30s / callTimeout 10min / retryOnConnectionFailure(true)`。

### 顺带加固
- 发 `Accept: text/event-stream` 头
- 分片解析失败时打 `Log.w` 日志（不再完全静默），便于定位
- 记录 `finish_reason`（`length` = 达到输出长度上限，属正常截断而非 bug）
- `trySend` 失败（下游关闭）才 break

## 新增：图片识别 + 模型切换为 deepseek-flash（2026-09-17，**已发布 v1.0.3**）

### 需求
用户要求增加图片识别功能；随后指定：**不用 GLM，默认模型与视觉模型都用 `deepseek-flash`**。

### 关键事实（已核实）
**DeepSeek 已支持图片输入**：V4.1 Flash 于 2026-09-10 正式发布，具备**原生多模态视觉理解**能力
（552B MoE / Causal-Encoder-Decoder 新结构）。所以 `deepseek-flash` 走图片识别可行，
base_url 仍是 `https://api.deepseek.com/v1`。

### 实现要点
1. **多模态消息模型**：`ChatMessage.content` 改为 `MessageContent`（text / parts 二选一），
   配套 `MessageContentSerializer`（自定义 KSerializer）：
   - 纯文本 → 序列化成 JSON **字符串**
   - 含图片 → 序列化成 OpenAI 多模态**分段数组**
     `[{"type":"image_url","image_url":{"url":"data:image/jpeg;base64,..."}},{"type":"text","text":"..."}]`
   - 反序列化两种形态都兼容
   - **坑**：`ListSerializer` 需 `import kotlinx.serialization.builtins.ListSerializer`
2. **图片处理** `data/image/ImageUtils.kt`：相册 Uri → BitmapFactory 解码 → 等比压缩到最长边 1280 →
   JPEG 质量 82 → 存 `filesDir/images/`；转 data URL 用 `Base64.NO_WRAP`。
3. **选图**：用 AndroidX `ActivityResultContracts.PickVisualMedia`（系统相册选择器，
   无需 READ_MEDIA_IMAGES 权限，低版本自动回落）。
4. **历史持久化**：`StoredMsg` 增加 `imagePath`——**只存文件路径不存 Base64**
   （一条 Base64 可数百 KB，会导致历史文件爆炸）。历史回放时图片**不重复上传**，
   仅在有图无文字时用「（用户发来了一张图片）」占位。
5. **UI**：输入区加图片按钮（图标 Image）；待发送图片预览条（可移除）；
   气泡内显示图片（`BitmapFactory.decodeFile` + `asImageBitmap`）+ 文字；
   有图无文字时占位提示「正在输入」判断需同时检查 imagePath。
6. **设置**：新增 `visionEnabled`（开关）+ `visionModel`（默认 `deepseek-flash`）；
   `Settings.modelFor(withImage)` 在发图时切换到视觉模型。
7. **模型默认值变更**：`deepseek-chat` → **`deepseek-flash`**（ProviderPresets + Settings + Repository），
   并在 Repository 里做了**旧值迁移**（读到 `deepseek-chat` 自动升级为 `deepseek-flash`），
   避免老用户卡在旧模型。
8. Persona 的能力描述补充"能理解文字和图片"；system prompt 在发图时附加图片能力说明
   （要求看图作答、看不清如实说明不要编造）。
