## 根因（重要）：图片/外网下载全失败 = 本机死系统代理
- 用户换网后重发动图仍 `[ERROR] 图片获取失败: 无法获取图片`，且「所有网页都死」。**根因不是 NapCat**（已把 `E:\NapCat\napcat\config\onebot11_2174298281.json` 的 `enableLocalFile2Url` 改为 true，但无效）。
- 真正根因：`HKCU\...\Internet Settings` 里 `ProxyEnable=1, ProxyServer=127.0.0.1:9098`（某 AI 桌面端如 `E:\QianwenApp\qianwen.exe` 注入的本地代理残留），但 9098 端口无任何进程监听 → 所有走系统代理的请求被甩给死地址 → `All connection attempts failed`。
- httpx 默认 `trust_env=True`，在 Windows 上会读取注册表系统代理（非仅 HTTP_PROXY 环境变量）→ 图片/视频/余额查询全被死代理卡死；但 `Test-NetConnection` / 强制 `trust_env=False` 直连 CDN 与百度均成功，证实新网络直连正常。
- 修复（两层）：①`E:\qq_bot\qq_plugin.py` 所有 `httpx.AsyncClient` 调用加 `trust_env=False`，`_system_proxy()` 增加 1.5s socket 可达性探测，代理不可达返回 None 回退直连（loopback 地址恒不走代理）；②必要时关闭系统代理 `Set-ItemProperty ... ProxyEnable 0` 即可恢复浏览器与 bot 全局直连。
- 用户澄清「从没用过代理软件」→ 该死代理是软件残留，不应再开；关掉即恢复。务必把 `trust_env=False` 同步回仓库 `libs/qq_bot_runtime/qq_plugin.py`（当前仅改了运行实例 E:\qq_bot）。
- 教训：**Windows 下 httpx 必须显式 `trust_env=False` 或统一代理管理**，不能依赖默认读系统代理；系统代理残留会同时拖垮浏览器与 bot。

## 修复：聊天不回话 + 记忆页失效（根因=孤儿 sidecar 端口 + WebView2 旧缓存 + App 桥接层滞后）
- 现象：App 控制台记忆页报 `加载失败: Cannot access 'renderers' before initialization`，且聊天无回复。
- 三大根因：
  1. **端口静默叠加**：今天 window 被反复重启 ~10 次，强杀主进程时 Windows 不连带杀子进程 → 旧 sidecar（memory/monitor/telemetry，端口 8766/8770/8771）残留；`ThreadingHTTPServer` 默认 `allow_reuse_address=1`(SO_REUSEADDR) 在 Windows 上允许多进程静默绑同一端口 → 每端口叠了 ~10 个监听，请求被随机路由到旧进程（记忆/监控数据错乱、聊天管线记忆调用不稳）。
  2. **WebView2 旧缓存**：用户窗口跑的是**很早的旧版 app.js**（含 `renderers` 的 TDZ bug + 错位的记忆 map），在 `no-store` 修复之前被启发式长缓存；旧 URL 无 `?v=` 一直命中缓存。
  3. **App 桥接层滞后**：`E:\feiyu_app\bridge\core_bridge.submit_chat` 仍是旧签名（无 `image_paths/video_path/audio_wav`），而 `server.py` 已传这些参数 → 每发消息 `TypeError` → 500 静默失败。引擎 `E:\qq_bot` 本身与仓库一致（robocopy 0 拷贝）。
- 修复（仓库提交，已同步部署副本并重启）：
  1. 四个 sidecar 服务（service_host/monitor_server/telemetry_server/vox_tts_server）改为 `_ExclusiveHTTPServer`（`allow_reuse_address=0` + `SO_EXCLUSIVEADDRUSE`），端口被占用直接失败而非静默叠加。
  2. `launcher_core/runtime.py` 新增 `_free_port`：生成 sidecar 前用 `netstat -ano` 找到端口上的残留监听并 `os.kill(SIGTERM)`（Windows SIGTERM=TerminateProcess），保证每次启动一组干净实例。
  3. `server.py`：`/static/` 路由剥离 `?v=`；`index.html` 注入 `/static/app.js?v=<mtime>`/`styles.css?v=<mtime>` 版本参数（配合 no-store）击穿 WebView2 旧缓存。
  4. `server.py` `/api/chat` 加 `try/except` 包住 `bridge.submit_chat`，异常记 degrade 并回 `{"ok":False,"error":...}` 而非裸 500。
  5. 部署同步：`robocopy libs/qq_bot_runtime → E:\qq_bot`（/E 不删额外文件）、`robocopy bridge → E:\feiyu_app\bridge` 与 `→ D:\testing\Fat-Fish\bridge`，把滞后的 App 桥接层拉齐。
- 验证：每端口单一 LISTENING；`/api/memory/*` 返回真实数据（profiles 含用户档案）；`POST /api/chat` 返回 `{"ok":true}`（无 500）；记忆页 `app.js?v=<mtime>` 已下发正确代码（map 与后端/renderers 对齐）。余额查询 `Illegal header value b'Bearer '` 为 balance_monitor 既有告警（空 key 供应商），与本次无关。
- 教训（新增 MEMORY.md）：①**Windows 上 `ThreadingHTTPServer` 必须显式独占绑定**，否则重复重启会静默叠加监听；②强杀主进程要连带清子进程，或在 launcher 生成前按端口清孤儿；③部署副本（E:\feiyu_app\bridge、E:\qq_bot）必须随仓库同步，否则会出现「server.py 已加参数、bridge 未接」的签名漂移导致 500；④静态资源加 `?v=<mtime>` 防 WebView2 旧缓存。
